# Large files

The studio holds files far larger than anything else in the platform: a 26 MB viewer, a
16 MB model, a 12 MB Blender scene, and two QA records of 18 MB and 2.5 MB. They are kept
in two storages, and which file goes where is decided by one question: does the site serve
it? This page explains the split, lists what sits where, and says what it costs.

## Why two storages

Two constraints pull in opposite directions.

**GitHub Pages serves an LFS pointer as text.** Git LFS keeps a short pointer in history and
the bytes elsewhere. The Pages build checks out without fetching LFS objects, so a file held
in LFS reaches the site as its pointer: a few lines naming an oid and a size, served where
the reader expected a model. Anything the site serves, or a browser reads, therefore has to
be an ordinary blob.

**A source a rebuild rewrites is history the clone carries forever.** Ordinary Git history
keeps every version of every file, so a large file that changes whenever the model is
rebuilt makes every clone heavier by its whole size, for good. A file nothing serves is
better in LFS, where history holds only the pointer and a clone fetches the bytes it needs.

So the sources the site never serves go through LFS, and everything it serves stays a blob.
The decision is [Decision 0006](../decisions/0006-sources-in-lfs-served-files-as-blobs.md).

## The patterns

`.gitattributes`, whole:

```text
* text=auto eol=lf

package-lock.json linguist-generated=true
uv.lock linguist-generated=true

# Large-file policy: docs/explanation/large-files.md. Sources the site never
# serves go through LFS; what the site serves, and what a browser reads, stays
# an ordinary blob because GitHub Pages serves an LFS pointer as text.
*.blend filter=lfs diff=lfs merge=lfs -text
assets/models/biscuit/qa/geometry/*.json filter=lfs diff=lfs merge=lfs -text
assets/models/biscuit/qa/native-samples.json filter=lfs diff=lfs merge=lfs -text

# Binary and generated: never normalised, never diffed, so a checkout is
# byte-identical to the commit and assets/manifest.json stays true.
*.glb -text -diff
*.png -text -diff
*.jpg -text -diff
static/pose-studio/viewer.html -text -diff linguist-generated=true
```

Line by line:

- `* text=auto eol=lf` normalises text files to LF, so no platform's checkout rewrites a
  line ending under a hash.
- The two lockfiles are marked generated so a review collapses them.
- `*.blend` goes to LFS wherever it is: a Blender scene is never served and is rewritten
  whole by every save.
- The two QA patterns name their paths exactly. They are JSON, which the site might one day
  serve elsewhere, so the pattern is a path rather than an extension.
- `*.glb`, `*.png` and `*.jpg` are binary: never normalised, never diffed, so the bytes a
  checkout writes are the bytes the manifest hashed.
- The viewer is text, but 26 MB of it, most of it base64. It is neither normalised nor
  diffed, and it is marked generated so a review does not try to render its diff.

## What is where

Every figure below is read from `assets/manifest.json`.

| `assets/models/biscuit/qa/geometry/rigged.json` | 17,750,241 | LFS | a QA record, regenerated by every rebuild, read by nothing on the site |
| `assets/models/biscuit/qa/native-samples.json` | 2,525,893 | LFS | the same |
| `static/pose-studio/viewer.html` | 27,561,668 | blob | served by Pages |

| `static/pose-studio/previews/pose-overview.jpg` | 398,799 | blob | linked from the viewer and shown on the model page |
| `assets/models/biscuit/textures/*.png` (36) | 10,040,783 | blob | sources, but small and rarely regenerated |

| `assets/illustrations/good/*.png` (11) | 15,137,724 | blob | imported by the gallery page |

The three LFS objects total 32,281,033 bytes, about 32.3 MB. The manifest lists 105 files,
111,680,319 bytes in all. The GLB and the overview live under `static/pose-studio/` only,
never duplicated under `assets/`, because the viewer links them relative to itself.

## What it costs

**Quota.** GitHub's free tier includes 10 GiB of LFS storage and 10 GiB of bandwidth a month,
with metered billing beyond that rather than pre-paid data packs, and a download counts
against the repository's owner, not the person cloning. Those figures were read from
GitHub's documentation on 2026-09-23 and may have moved since. A clone that fetches the three
objects spends about 0.3% of a month's bandwidth, and every rebuild that changes all three
adds another 32 MB of storage.

**History.** Every rebuild of the viewer adds 26 MB of ordinary history, and the GLB another
16 MB, because both are served and so cannot be in LFS. That is accepted while rebuilds are
rare and approved one at a time; the exit is a viewer that loads the GLB instead of inlining
everything, which would leave one served file instead of two.

**Setup.** git-lfs is installed once per machine, and `git lfs install --local` runs in each
clone; `scripts/initialize.sh` does the second. A clone made without git-lfs sees 133 bytes
of pointer text where the `.blend` should be. A contributor without it who commits a changed
`.blend` stores the real file as an ordinary blob, and nothing in the gate notices: the
checker compares the manifest with `.gitattributes`, which still names the path, and hashes
the file's bytes, which are the right ones. [Troubleshooting](../operations/troubleshooting.md)
says how to see it.

**CI.** Every checkout in CI is `lfs: false`. The asset checker verifies an LFS-tracked file
from its pointer, which carries the object's sha256 and size, so no job fetches an object
and CI spends none of the bandwidth.

## The risk

A served path moved under an LFS pattern would deploy pointer text, silently. The Pages build
does not fetch LFS objects, the build would succeed, and the site would serve a few lines of
text where the viewer or the GLB should be. That is why the patterns name sources by path
rather than by broad extension: a rename that puts a served file under
`assets/models/biscuit/qa/geometry/`, or a new pattern broad enough to catch `.html` or
`.glb`, is the change that breaks the site. `just check-assets` refuses a manifest whose
`storage` disagrees with `.gitattributes`, which catches the move only if the manifest was not
rewritten with it; the other guard is reading the diff of `.gitattributes` whenever it
changes.

## The three rewritten hrefs

The viewer came from the source repository linking three things relative to itself: the
`.blend` twice and the model's README once. Neither is served here — the `.blend` is an LFS
object and the README lives under `assets/` — so the three attribute values were rewritten,
and only those, to the files' pages on GitHub in this repository, on the `main` branch.
GitHub renders an LFS file's page with a download button, so a reader of the site can still
fetch the `.blend` in one click.

The manifest's entry for the viewer records the rewrites in its `patched` field and the
unpatched page's digest in `source_sha256`, so the difference from the source is written
down rather than discovered. The links point at `main`: a branch rename, or a move of either
file under `assets/models/biscuit/`, breaks them inside a file no linter reads.

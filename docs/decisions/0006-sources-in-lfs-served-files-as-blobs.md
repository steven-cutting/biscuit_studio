# Decision 0006: Sources in LFS, served files as blobs

## Context

The approved model arrived as a package of 94 files and about 92 MB. Three of its files are
far larger than anything a Biscuit Games repository has held: the viewer is a single 26 MB
HTML page with every texture and all the geometry inlined, the GLB is 16 MB, and the native
`.blend` is 12 MB. Two QA records are large JSON files a rebuild regenerates.

Ordinary Git history keeps every version of every file forever, so a large file that
changes often makes every clone heavier. Git LFS keeps a pointer in history and the bytes
elsewhere, but GitHub Pages cannot serve an LFS object: a Pages artefact built from a
checkout that did not fetch the object contains the pointer text, and the site serves it.

GitHub's free tier includes 10 GiB of LFS storage and 10 GiB of bandwidth a month,
metered beyond that, and a download counts against the repository's owner. The figure was
read from GitHub's documentation on 2026-09-23.

## Decision

Sources the site never serves go through LFS; what the site serves stays an ordinary blob.
`.gitattributes` says which, by three patterns:

```text
*.blend filter=lfs diff=lfs merge=lfs -text
assets/models/biscuit/qa/geometry/*.json filter=lfs diff=lfs merge=lfs -text
assets/models/biscuit/qa/native-samples.json filter=lfs diff=lfs merge=lfs -text
```

| Path | Storage | Why |
| --- | --- | --- |
| `assets/models/biscuit/model/biscuit-poseable.blend` | LFS | The native source; every rebuild rewrites all of it. |
| `assets/models/biscuit/qa/geometry/rigged.json` | LFS | A QA record, regenerated by every rebuild, read by nothing on the site. |
| `assets/models/biscuit/qa/native-samples.json` | LFS | The same. |
| `static/pose-studio/viewer.html` | blob | Served by Pages. |
| `static/pose-studio/model/biscuit-poseable.glb` | blob | Linked from the viewer and the model page; served by Pages. |
| `static/pose-studio/previews/pose-overview.jpg` | blob | Linked from the viewer. |
| `assets/models/biscuit/textures/`, `previews/` | blob | Sources, but small and rarely regenerated. |
| `assets/illustrations/good/` | blob | Imported by the gallery page. |

The binary files are marked `-text -diff` as well, so a checkout is byte-identical to the
commit and the manifest's hashes stay true. Every CI checkout is `lfs: false`, and the
asset checker verifies an LFS-tracked file from its pointer, which carries the object's
sha256 and size, so CI never fetches an object.

## Consequences

**Every rebuild of the viewer adds 26 MB of ordinary history.** Accepted while rebuilds
are rare and approved. The exit is porting the viewer to a maintained component that loads
the GLB rather than inlining everything; see
[Decision 0008](0008-the-viewer-is-embedded-as-is.md).

**Git LFS has to be set up before the first commit that touches the model.** git-lfs is
installed once per machine and `git lfs install --local` runs in each clone;
`just initialize` does the second. A contributor without it adds a real `.blend` as an
ordinary blob, which nothing can see before `git add`; from then on the checker reads the
index and refuses a path LFS should hold that is not a pointer.

**A served path moved into LFS silently breaks the site.** The patterns name sources by
path, so a rename that put a served file under one would deploy pointer text, and no build
step would fail.

**The quota is comfortable, not infinite.** The three LFS objects are about 32 MB, so a
clone that fetches them spends about 0.3% of a month's free bandwidth. Every rebuild adds
another 32 MB of storage.

## What would reopen this

The LFS quota running out, or its terms changing. The viewer being retired in favour of a
component that serves the GLB, which would remove the largest ordinary blob. A second
model, which would double both costs and might move the line between source and served.
